# GreenLight – проектный промт

## 1. Общее описание

GreenLight – умный светильник на ESP32 с управлением через мобильное Flutter-приложение и MQTT-сервер.

Цели:

- Локальное управление светильником без интернета и без аккаунта.
- Облачное управление через аккаунт, домашний Wi‑Fi и MQTT.
- Сохранение локально найденных светильников на телефоне.
- Постепенное развитие от локального режима к безопасной аккаунтной привязке и удалённому управлению.

## 4. ESP32 и прошивка

- Плата: ESP32.
- Светильник работает в двух режимах:
  - `AUTO` – яркость по расписанию.
  - `MANUAL` – пользователь вручную включает/выключает светильник и меняет яркость.

### Локальный HTTP API

Светильник поднимает Wi‑Fi access point и HTTP-сервер по адресу `192.168.4.1`, порт `80`.

- `GET /status` – возвращает строку `ON|OFF currentBrightness mode connectivityStatus`.
- `GET /info` – возвращает JSON с данными прошивки, `mqttDeviceId` и информацией о продукте.
- `GET /schedule` – возвращает до восьми интервалов расписания: по одному интервалу в строке, формат `enabled,startHour,...,fadeMinutes`.
- `POST /schedule` – применяет расписание; требует параметр `key == authSecret`.
- `POST /command` – принимает команды:
  - `ON`
  - `OFF`
  - `BRIGHT:xx`
  - `MODEAUTO`
  - `MODEMANUAL`
  - Все защищённые команды требуют `key == authSecret`.
- `POST /wifi` – принимает домашние Wi‑Fi credentials (`ssid`, `password`, `key`), сохраняет их в NVS, подключает ESP32 к роутеру и запускает NTP.

### Идентификаторы и безопасность ESP32

- `authSecret`:
  - Генерируется при первом запуске устройства как случайная HEX-строка.
  - Хранится в NVS.
  - Печатается в QR-коде светильника.
  - Используется как параметр `key` для защищённых локальных HTTP-запросов.
  - Реальное значение `authSecret` никогда не публиковать в GitHub, prompt-файлах, чатах или логах.

- MQTT:
  - `mqttDeviceId` основан на STA MAC-адресе ESP32.
  - `mqttUsername` и `mqttPassword` генерируются устройством и хранятся в NVS.
  - MQTT-темы:
    - `lamp/<mqttDeviceId>/status`
    - `lamp/<mqttDeviceId>/command`
    - `lamp/<mqttDeviceId>/schedule`
  - Реальные MQTT credentials никогда не публиковать в GitHub, prompt-файлах, чатах или логах.

## 5. Flutter-приложение

### Основные файлы

- `lib/main.dart` – запускает `GreenLightApp`.
- `lib/screens/welcome_screen.dart` – стартовый экран:
  - **«Войти в аккаунт»** открывает `AuthLoginScreen`.
  - **«Создать аккаунт»** открывает `AuthRegisterScreen`.
  - **«Продолжить без аккаунта»** открывает `DevicesScreen` для локального управления без интернета и без аккаунта.

- `lib/screens/auth_login_screen.dart`:
  - Экран входа по email и паролю.
  - Выполняет `POST /auth/login`.
  - Получает token из JSON-ответа.
  - Сохраняет token через `AuthStorage.saveToken(token)`.
  - После успеха открывает `DevicesScreen`.

- `lib/screens/auth_register_screen.dart`:
  - Экран регистрации по email.
  - Поля: email, пароль, галочка согласия на обработку персональных данных.
  - Выполняет `POST /auth/register` с JSON `{email, password, consent}`.

- `lib/screens/auth_verify_screen.dart`:
  - Экран ввода кода подтверждения.
  - Отправляет код на FastAPI backend.
  - При успешном подтверждении получает token.
  - Сохраняет token через `AuthStorage.saveToken(token)`.
  - После успеха открывает `DevicesScreen`.

- `lib/services/auth_storage.dart`:
  - Использует `flutter_secure_storage`.
  - Хранит auth token под ключом `gl_auth_token`.
  - Методы:
    - `saveToken(String token)`
    - `readToken()`
    - `deleteToken()`

- `lib/screens/devices_screen.dart`:
  - Экран «Мои светильники».
  - Показывает локально сохранённые/обнаруженные устройства.
  - Открывает управление выбранным светильником.
  - Должен содержать действие добавления нового светильника через QR/AP.

- `lib/screens/lamp_control_screen.dart` – управление яркостью и режимами светильника.
- `lib/screens/lamp_schedule_screen.dart` – редактирование расписания; сохранение отправляет `POST /schedule` на ESP32.
- `lib/screens/qr_scanner_screen.dart` – сканирование QR-кода точки доступа и данных светильника.

### Авторизация

- Flutter использует публичный HTTPS API `https://greenlight-lamp.ru/auth/...`.
- После login или verify backend должен возвращать JSON с полем `token`.
- Token не логировать, не отображать на экране, не записывать в исходный код и не коммитить.
- Token хранится через `flutter_secure_storage`, а не в открытом файле или `SharedPreferences`.
- Login, регистрация и подтверждение кода должны показывать понятные ошибки сети и backend, не раскрывая секретные данные.

### Локальные и аккаунтные устройства

- Сейчас `DevicesScreen` показывает локально сохранённые устройства на конкретном телефоне.
- Появление тестового светильника после login/verify не означает его облачную привязку к аккаунту: это ранее сохранённое локальное устройство.
- Будущая облачная модель требует:
  - Привязки `user_id ↔ mqttDeviceId` на backend.
  - Проверки `authSecret` из QR-кода при первоначальной привязке.
  - API списка устройств текущего пользователя, например `GET /devices`.
  - Получения и отображения облачного списка по auth token.
  - Ясного разделения или объединения локальных и аккаунтных светильников в интерфейсе.
- Локальный режим всегда должен оставаться доступен без аккаунта и без интернета.

## 6. Потоки использования

### Без аккаунта

1. Пользователь запускает приложение и видит `WelcomeScreen`.
2. Нажимает «Продолжить без аккаунта».
3. Переходит на `DevicesScreen`.
4. Сканирует QR-код светильника и подключается к AP/HTTP API по `192.168.4.1`.
5. Управляет светильником локально: яркость, режимы и расписание.
6. Интернет и аккаунт не требуются.

### Регистрация

1. На `WelcomeScreen` пользователь нажимает «Создать аккаунт».
2. Открывается `AuthRegisterScreen`.
3. Пользователь вводит email и пароль, подтверждает согласие.
4. Flutter вызывает `POST /auth/register`.
5. Backend создаёт пользователя и генерирует код подтверждения.
6. Пользователь вводит код в `AuthVerifyScreen`.
7. Backend подтверждает email и возвращает token.
8. Flutter сохраняет token в secure storage и открывает `DevicesScreen`.

### Вход

1. На `WelcomeScreen` пользователь нажимает «Войти в аккаунт».
2. Открывается `AuthLoginScreen`.
3. Пользователь вводит email и пароль.
4. Flutter вызывает `POST /auth/login`.
5. Backend возвращает token.
6. Flutter сохраняет token в secure storage и открывает `DevicesScreen`.

### Облако и MQTT в будущем

После безопасной привязки светильника к аккаунту пользователь сможет:

- Передать светильнику настройки домашнего Wi‑Fi.
- Получить MQTT credentials, связанные с устройством.
- Управлять светильником удалённо через MQTT.
- Просматривать статус светильника без локального подключения к AP.
- Использовать облачный список светильников аккаунта.

## 7. Навигация после авторизации

- `DevicesScreen` («Мои светильники») является главным экраном после успешного входа или подтверждения регистрации.
- На `DevicesScreen` не добавлять обычную стрелку «Назад» для возврата на `WelcomeScreen`: пользователь уже авторизован, и это не обычный возврат к предыдущей форме.
- В будущем добавить в AppBar меню профиля или настроек.
- В меню предусмотреть явное действие «Выйти из аккаунта».
- При logout удалить auth token через `AuthStorage.deleteToken()`, очистить navigation stack и открыть `WelcomeScreen`.
- Logout не должен удалять локально сохранённые светильники: они должны оставаться доступны в режиме без аккаунта.
- В будущем интерфейс должен ясно различать локальные светильники и светильники, привязанные к аккаунту и облачному управлению.

## 8. Проверка на Android

### Тестовое устройство

- Модель: `M2007J20CG`.
- ОС: Android 12, API 31.
- Архитектура: `android-arm64`.
- Flutter device ID при USB-подключении: `55530726`.

### Полезные команды

Проверить подключение телефона:

```cmd
flutter devices
```

Запустить Flutter-приложение на тестовом телефоне:

```cmd
flutter run -d 55530726
```

Если device ID изменится, использовать новый ID из результата `flutter devices`.

### Подтверждённые ручные проверки

- Flutter-приложение успешно собирается, устанавливается и запускается на M2007J20CG.
- Стартовый экран открывает login, регистрацию и локальный режим.
- На login screen работают поля email/пароль, переключатель видимости пароля и проверка пустой формы.
- Регистрация нового пользователя, подтверждение кода и переход к `DevicesScreen` успешно проверены.
- Вход существующего пользователя и переход к `DevicesScreen` успешно проверены.
- После login/verify ранее добавленный тестовый светильник отображается на `DevicesScreen` как локально сохранённое устройство.

## 9. Правила работы с ассистентом

1. Работать неспеша, по одному блоку команд:
   - сначала обсудить идею и цель шага;
   - затем дать один конкретный набор команд или полный файл;
   - после результата пользователя проверить вывод и перейти к следующему шагу.

2. При большой правке ассистент даёт полный файл, например `welcome_screen.dart` или `auth_register_screen.dart`, чтобы его можно было открыть через:

```cmd
notepad lib\screens\file.dart
```

Затем пользователь заменяет содержимое через `Ctrl+A`, вставляет полный текст и сохраняет файл.

3. Не придумывать новые файлы, endpoint’ы, JSON-поля, модели данных или имена без согласования и проверки текущего кода.

4. Перед изменениями ассистент:
   - сверяется с актуальным GitHub-кодом Flutter-репозитория;
   - при API-изменениях сверяется с актуальным GitHub-кодом backend-репозитория;
   - при ESP32-изменениях сверяется с актуальной прошивкой;
   - учитывает этот файл `docs/project_prompt.md` как источник правил и принятых решений;
   - не предполагает, что файл прочитан, если инструмент вернул только SHA/служебное сообщение вместо текста.

5. Перед необратимыми действиями:
   - показать точный набор меняемых файлов и ожидаемый результат;
   - проверить diff;
   - запросить подтверждение перед commit, push, созданием GitHub-файла, изменением сервера или отправкой сообщений;
   - не публиковать пароли, token, `authSecret`, MQTT credentials, приватные ключи, `.env` или персональные данные без необходимости.

6. Утренний старт работы:
   - пользователь указывает Flutter-репозиторий, backend-репозиторий и актуальную прошивку ESP32, если задача её касается;
   - ассистент сверяет актуальные коммиты и значимые файлы;
   - затем предлагает следующий минимальный безопасный шаг.
